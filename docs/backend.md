# Together backend

Requires Node 24. Run `npm install`, copy `.env.example` to `.env`, then `npm run dev`. Open the frontend on localhost:5173. On a local development installation with SETUP_CODE empty, the first person registers directly without a code. This exception requires a loopback connection and localhost Host, is disabled in production, and closes after the first account. A configured SETUP_CODE is mandatory in production. After signing in, GET /api/invite provides the private code for the second member. Registration closes permanently at two users. Keep setup and invitation codes private. Passwords require 12 characters. A WhatsApp number in international E.164 format is required, including + and country code with no spaces.

The API defaults to loopback port 3001. Development permits the listed localhost origins. For deployment, set NODE_ENV=production, APP_ORIGIN to the exact HTTPS public origin, HOST as required by your hosting environment, DATABASE_PATH to a persistent private volume, and a strong SETUP_CODE. Serve HTTPS through a trusted reverse proxy. Production cookies are Secure, HttpOnly, SameSite=Strict, and expire after seven days. SQLite stores private household data unencrypted on disk; restrict file access and protect encrypted backups. Do not commit `.env`, database files, or backups. There is no account recovery UI in this initial version.

## Contract

GET /api/setup is public and returns needsSetup, registrationOpen, setupConfigured. POST /api/register accepts name, email, password, whatsapp (required +country-code international digits), inviteCode. POST /api/login accepts email/password. Both return `{user}` and set the session cookie. POST /api/logout invalidates it.

Other routes require authentication. GET /api/state?month=YYYY-MM returns the contract in implementation.md; the default month is Asia/Kolkata. Drafts are returned only to their author. GET /api/invite returns `{inviteCode}` when only one member exists. Topics and goal/agreement/appreciation mutations return the complete updated object. POST /api/notifications/read and logout return `{ok:true}`. Errors are JSON `{error}` with suitable 4xx/5xx status.

POST /api/topics accepts title, description, category, draft. Publishing requires a second household member. PATCH /api/topics/:id takes action publish, schedule, or resolve. Only the author may publish a draft; only the recipient may schedule a published topic. Schedule requires date YYYY-MM-DD and time HH:mm in Asia/Kolkata; duration defaults to 30 minutes (15–240). The entire appointment must be in a future Saturday/Sunday interval, with no overlap. Either member can resolve a published topic and record outcome. Draft editing and topic deletion are not supported.

POST /api/goals takes title, target (positive), current (nonnegative, default zero), unit. PATCH /api/goals/:id sets current. POST /api/agreements accepts text and initially accepts for the author. PATCH /api/agreements/:id accepts for the current user idempotently. POST /api/appreciations takes text.

PUT /api/finance takes month, revision, income, expenses, savings, accounts, transfers. State returns revision (initially 0); each successful save increments it. Income updates only the signed-in member's amount, preserving the partner's. All finance fields are specific to the selected month. Accounts are `{id,name,last4,purpose}`; store only the last four digits. IDs must be unique. Purpose is Household, Savings, or Personal; at most one Household and one Savings account is allowed per month because each represents the full corresponding target. Transfers are account ID strings checked as completed, representing a checklist only. This app does not connect banks or move funds. A stale revision is rejected with HTTP 409 without changing any values. Reload the selected month and review the latest plan before retrying. This prevents stale shared expense/savings/account/checklist updates from overwriting changes made by the partner.

## Notifications

Creating/publishing a topic notifies its recipient; scheduling notifies its author. Content in external notifications is generic and excludes topic title, description, outcome, finances, and appreciation text. Each event immediately persists an in-app notification and two outbox records. State exposes notification `title`, `emailStatus`, `whatsappStatus`, and `delivery:[{channel,status,attempts}]`. Integration is `{email:{configured:boolean},whatsapp:{configured:boolean}}`.

The worker runs every 30 seconds. SMTP requires SMTP_HOST and SMTP_FROM, plus credentials when the provider requires them. OpenWA requires OPENWA_BASE_URL, OPENWA_API_KEY, and OPENWA_SESSION_ID, and the recipient's international phone number. Adapter contract: POST `/api/sessions/{sessionId}/messages/send-text`, header X-API-Key, JSON `{chatId:'digits@c.us',text}`. Configure a compatible authenticated OpenWA service. Use an HTTPS provider endpoint outside a trusted local network.

Statuses are pending, not_configured, retry, failed, accepted. `accepted` means provider accepted the request, not confirmed recipient delivery. Missing credentials or a missing WhatsApp number produce not_configured; no provider success is fabricated. Up to four delivery attempts occur with exponential backoff and ten-second network timeouts. Delivery is at-least-once; a crash after provider acceptance may cause a duplicate. Missing configuration is rechecked each minute. Environment changes require process restart.

On the seventh in Asia/Kolkata the worker creates a monthly finance reminder for both members once per month, deduplicated in SQLite. During the hour before a scheduled discussion, the worker also reminds both members once for that specific topic/time. Rescheduling creates a new reminder identity. Resolved discussions are excluded. The server must be running during these windows; it does not backfill missed reminders or months. No live messages are sent by automated tests.

Run `npm test` for integration tests using an isolated temporary SQLite database and localhost HTTP server. Coverage includes setup/invitation restrictions, authentication/logout, CSRF origin rejection, draft isolation, recipient-only future-weekend scheduling, overlaps, monthly incomes, persistence, missing-provider statuses, monthly and discussion reminder deduplication, correct notification recipients, exact OpenWA adapter requests, bounded retries, and provider acceptance.
